## 阶段 3：接入 LangGraph Checkpointer

### 目标

使用 LangGraph 的 Checkpointer（状态检查点保存器）保存线程级短期状态，支持连续对话、失败恢复和中断恢复。

### 增量工作

- [x] 使用官方 `langgraph-checkpoint-postgres` 和 `AsyncPostgresSaver`。
- [x] 在全新的 PostgreSQL `agent_app` 数据库中初始化，不迁移旧的 agent_app 数据。
- [x] PostgreSQL 只承载会话历史和 LangGraph Checkpointer，MySQL 只承载 Olist 分析数据及 Meta 数据。
- [x] 配置图编译时使用持久化 Checkpointer。
- [x] 统一使用 conversation_id 作为 thread_id。
- [x] 明确限制 SQLAlchemy 自动建表范围，只创建四张会话业务表。
- [x] 每次新轮次显式清空临时 State，避免 Checkpointer 把上一轮 SQL、rows、报告和召回结果带入下一轮。
- [x] 验证业务会话历史的写入、读取和删除。
- [x] 验证关闭并重新初始化服务后可以恢复同一 thread_id 的检查点状态。
- [ ] 验证失败和中断后的恢复路径。
- [ ] 统计 Checkpoint 体积和保存耗时。

### 状态边界

短期会话状态可以保留：

~~~text
最近消息
会话摘要
最新轮次和最新结果引用
当前数据源范围
~~~

当前轮次临时数据只在执行期间使用，后续逐步外置：

~~~text
完整 rows
完整事件
大批量召回候选
完整 Python 输出
~~~

### 阶段验收

- [x] 同一 conversation_id 使用同一个 thread_id，后续请求不会复用上一轮的临时查询字段。
- [x] Checkpointer 使用独立的 thread_id 隔离不同会话；真实跨会话业务执行验证留待阶段 4/5 联调。
- [x] Checkpoint 表由官方 `AsyncPostgresSaver.setup()` 管理，不与业务历史表重复定义。
- [x] Checkpoint 不直接作为前端聊天历史接口，前端仍读取现有会话历史接口。
- [ ] Checkpoint 不保存无限增长的完整结果数据。
- [ ] 失败和中断后可以恢复到可继续执行的节点。

### 阶段 3 实现边界

本阶段只完成 PostgreSQL 持久化和线程级检查点接入，不读取会话历史给 LLM，也不实现
阶段 4 的多轮问题补全。会话历史由 `conversations`、`conversation_turns`、
`conversation_messages` 和 `turn_outputs` 四张业务表管理；LangGraph 官方表由
`AsyncPostgresSaver.setup()` 管理。两套数据都在 PostgreSQL 中，但职责和访问入口保持分离。

## 阶段 4：增加上下文构建和多轮问题补全

### 目标

让用户可以使用“那 11 月呢”“继续刚才的分析”这类省略表达，系统在进入业务节点前补全问题。

### 增量工作

- [x] 增加独立的通用 ContextEngine 内核，完成上下文收集、隔离、选择、组织、压缩和追踪。
- [x] 增加独立 /api/daily-chat 日常聊天入口，作为 ContextEngine 的首个真实应用适配。
- [x] 日常聊天读取当前会话消息，保存上下文选择追踪，并不经过数据分析节点。
- [x] 日常聊天本轮结果保存为普通文本消息，不创建 LangGraph 分析运行。
- [x] 提供按会话轮次读取 context_trace 的调试接口，不重复返回完整历史内容。
- [ ] 增加 Data Agent 的 ContextSource、ContextPolicy 和 ContextBuilder 应用适配层。
- [ ] 读取当前会话最近几轮消息。
- [ ] 读取上一轮结构化结果摘要和结果引用。
- [ ] 生成本轮 resolved_question（补全后的完整问题）。
- [ ] 记录本轮使用了哪些历史轮次作为 context_refs。
- [ ] 先采用最近消息和最近结果摘要，不做向量化历史搜索。
- [ ] 只在路由和问题补全阶段使用会话上下文。
- [ ] 后续召回、SQL、Python 和报告节点继续接收各自最小上下文。

### 上下文边界

~~~text
路由/问题补全：当前问题 + 最近消息 + 最近结果摘要
元数据召回：resolved_question + 当前任务术语
生成 SQL：当前任务 + 相关元数据 + 必要的历史查询条件
执行 SQL：SQL
Python 分析：当前任务结果 + 必要的依赖摘要
报告规划：分析证据 + 任务摘要 + 有限预览
决策支持：报告摘要 + 分析证据摘要 + 用户当前问题
~~~

### 阶段验收

- [ ] “那 11 月呢”可以被补全为明确的数据问题。
- [ ] “继续刚才的分析”可以找到对应的上一轮结果。
- [ ] 普通聊天不会把 SQL、rows 和节点日志带入上下文。
- [ ] 多轮上下文不会改变现有分析节点的职责。

## 阶段 5：支持日常聊天与问数/分析任意顺序切换

### 目标

让一条会话中可以任意交替出现日常聊天、简单问数和数据分析。

### 路由定义

- [ ] chat：日常聊天，只返回文字，不调用 SQL 和 Python。
- [ ] simple_data：简单问数，返回文字、数值、表格或简单图表，不生成完整报告。
- [ ] analysis：多任务分析，返回文字、表格、图表和 RenderedReport。
- [ ] decision_support：先保留未实现状态，暂不进入正式执行。
- [ ] needs_clarification：表示当前问题信息不足，不作为独立业务类型。
- [ ] 路由失败时不再无条件回退到简单问数，避免复杂问题被错误执行。

### 增量工作

- [ ] 在现有路由后增加日常聊天分支。
- [ ] 将 resolved_question 传给现有问数和分析链路。
- [ ] 保证每条助手消息只渲染它自己的输出，不覆盖前一轮内容。
- [ ] 根据响应类型决定是否显示“查看查询过程”或“查看分析过程”。
- [ ] 支持聊天、问数、分析、聊天、问数的混合顺序。

### 阶段验收

- [ ] 日常聊天不触发数据查询。
- [ ] 简单问数不强制生成完整报告。
- [ ] 分析问题仍然走现有分析任务和报告链路。
- [ ] 同一会话中三类消息可以连续展示。
- [ ] 任意一轮都可以单独查看自己的输出和执行过程。

## 阶段 6：增加决策支持 Agent

### 目标

在已有分析结果上增加“原因判断、处理建议、优先级、风险和后续验证”的决策支持能力。

### 输入边界

决策支持只接收：

~~~text
用户当前问题
上一轮 RenderedReport 摘要
关键分析发现
分析任务摘要
证据引用
报告限制
~~~

默认不接收：

~~~text
完整 AgentState
完整 rows
全部 SSE 事件
全部召回候选
无关历史 SQL
~~~

### 增量工作

- [ ] 定义决策支持结果结构：关键发现、可能原因、建议动作、优先级、风险限制、待验证事项。
- [ ] 增加决策支持路由分支。
- [ ] 读取同一会话中最近的分析报告和证据摘要。
- [ ] 生成面向用户的决策建议。
- [ ] 对“数据支持的结论”和“需要进一步验证的推断”进行区分。
- [ ] 在前端增加“查看决策依据”入口。
- [ ] 暂不执行写数据库、发通知或其他真实业务动作。

### 阶段验收

- [ ] 用户可以针对上一份分析报告继续提问并得到建议。
- [ ] 建议能指向具体分析发现和证据。
- [ ] 没有证据的原因会标记为待验证，而不是直接表述为事实。
- [ ] 决策支持结果可以在聊天消息中渲染，并可查看依据。

## 阶段 7：完善 Harness 运行循环和可靠性

### 目标

把 Harness（模型运行控制层）落实为“判断、执行、观察、继续或结束”的受控循环，提高复杂任务的成功率和可恢复性。

### 循环范围

~~~text
会话循环：用户提问 -> Agent 执行 -> 保存结果 -> 用户继续提问
任务循环：检查依赖 -> 执行任务 -> 保存结果 -> 执行后续任务
修正循环：生成 SQL/Python -> 执行 -> 失败时有限修正 -> 再执行
~~~

### 增量工作

- [ ] 建立 agent_runs，记录一次执行尝试。
- [ ] 建立 agent_run_events，记录节点、工具、状态、耗时和错误。
- [ ] 建立 agent_task_results，记录任务结果、摘要、预览和结果引用。
- [ ] 实时 SSE 事件与持久化执行记录同时保留。
- [ ] 为 SQL 失败增加最多 1 至 2 次的有限修正。
- [ ] 为 Python 失败增加最多 1 至 2 次的有限修正。
- [ ] 记录超时类型、发生节点、请求参数摘要和最后一个事件。
- [ ] 支持用户取消运行。
- [ ] 保证重试不会重复写入错误的最终消息。
- [ ] 为同一会话增加并发执行保护。
- [ ] 为工具调用增加只读、权限和数据量边界。

### 阶段验收

- [ ] 前端可以按照 turn_id 打开对应的查询或分析过程。
- [ ] 失败任务可以定位到具体节点、工具和错误。
- [ ] SQL 或 Python 不会无限自动重试。
- [ ] 断开连接后，后端运行状态和最终结果仍然可查询。
- [ ] 重试、超时和取消不会污染下一轮会话上下文。

## 三、每个阶段的固定工作方式

每次开发按下面的顺序执行：

1. [ ] 先确认本阶段只解决一个能力目标。
2. [ ] 先读取当前代码和 Git 状态，不覆盖用户已有修改。
3. [ ] 只增加本阶段需要的字段、模块或接口。
4. [ ] 不修改数据源、指标、维度、术语和对应代理。
5. [ ] 完成后做必要的静态检查和针对性验证。
6. [ ] 更新本文件的勾选状态和当前阶段说明。
7. [ ] 整理本次改动并提交一次 Git commit。
8. [ ] 下一阶段开始前，先确认上一阶段验收条件已经满足。
